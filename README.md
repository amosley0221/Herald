# Herald

An automated job application engine. It reads your resume, scans every posting
published since it last looked, scores each one against your background and
preferences, and brings you only the ones worth your time — instantly for the
strong matches, in a morning digest for the rest. When you approve one, it fills
in the application and shows you exactly what it will send. Nothing goes out
without your explicit Submit.

Two clients, one engine:

| | |
|---|---|
| **Android app** | Expo / React Native. Updates over the air — no reinstall. |
| **Desktop app** | Tauri (Windows, macOS, Linux). Self-updating, signed. |
| **Engine** | Node service. Crawls, scores, prepares and submits. |

---

## What runs where

```
herald/
├── packages/core/      Contracts, design tokens, copy, API client — shared by all three
├── services/engine/    The scheduled service: crawl → score → prepare → submit
├── apps/android/       Expo app
├── apps/desktop/       Tauri app
├── scripts/            Version sync, icon and token generation, release tooling
└── releases/           Generated by CI: the feed both in-app updaters read
```

The apps are thin clients. All of the work — and all of your data — lives in the
engine, which is yours to host. Nothing is hardcoded: job sources, prompts,
form-field rules, models, schedules and thresholds are all configuration.

## Setting it up

### 1. The engine

You need somewhere always-on for the daily scan. A $5/month VPS is plenty; so is
a machine at home that stays awake. The Android app must not depend on your
desktop being on, which is why this is a service rather than a desktop feature.

```bash
git clone https://github.com/amosley0221/herald.git
cd herald
npm install
npm run build

# Generates herald.config.json and your access token
npm run init -w @herald/engine
```

Then, in that order:

1. **Set your API key.** Copy `services/engine/.env.example` to `.env` and fill in
   `ANTHROPIC_API_KEY`. Scoring, cover letters and resume parsing all need it.

2. **Choose your sources.** Open `herald.config.json` and replace the example
   entries under `sources` with the companies you actually want watched:

   ```jsonc
   {
     "id": "greenhouse",
     "adapter": "greenhouse",
     "priority": 10,
     "options": { "boards": ["stripe", "figma", "notion"] }
   }
   ```

   Four adapters cover the named ATSes — `greenhouse`, `lever`, `ashby`,
   `workday`. Two more cover everything else without writing any code:

   - `json` maps any JSON endpoint onto Herald's shape through a `fieldMap`.
   - `command` runs an external aggregator CLI and reads postings from stdout.

   `priority` decides who wins when the same job appears twice: put the ATS
   original above any aggregator so a duplicate collapses onto the real posting.

3. **Start it.**

   ```bash
   npm run engine
   # or: docker compose up -d --build
   ```

The engine serves on `:8787`. Put it behind TLS if it is reachable from the
internet — the token is the only thing between the outside world and your
resume.

### 2. The desktop app

```bash
npm run tauri:dev -w @herald/desktop     # development
npm run tauri:build -w @herald/desktop   # installers
```

On first launch it asks for the engine address and the token `npm run init`
printed. After that, Preferences shows a QR code for pairing your phone.

### 3. The Android app

The APK is built by CI and published to the repository's Releases page — see
[Cutting a release](#cutting-a-release). Download it on your phone, allow
"install unknown apps" for your browser when prompted, and install.

That is the only manual install you will ever do; every version after it
arrives on its own.

To build one locally instead, you need the Android SDK and a JDK:

```bash
cd apps/android
npx expo prebuild --platform android
cd android && ./gradlew assembleRelease
```

Without signing properties that produces a debug-signed APK, which installs
fine but cannot be updated over by a CI build. Use it for testing only.

Open the app, scan the QR code from the desktop app, upload your resume, set
your threshold. That is the whole of onboarding.

## How it decides

Each hour the engine runs one pass:

1. **Ingest** — pull everything published since the last run, from every enabled
   source, in parallel.
2. **Dedupe** — hash on company, normalized title and location, so the same job
   on three boards is one row. `Sr. Product Designer (Remote)` and
   `Senior Product Designer` collapse together.
3. **Prefilter** — your roles, locations, salary floor and excluded keywords,
   applied as cheap string rules. This drops the large majority before any model
   call, which is what keeps the cost down.
4. **Score** — one model call per surviving posting, with your resume and
   preferences, returning a 0–100 score, three reasons it fits and one or two
   gaps. Scores are cached by posting content, so nothing is ever scored twice.
5. **Route** — at or above your threshold, push immediately. Below it, wait for
   the morning digest at your local hour.

Scores below `matching.feedFloor` (60 by default) never become matches at all,
so lowering your threshold later cannot resurrect something already judged
unfit.

## What it will not do

These are deliberate, and they are enforced in code rather than left to
configuration:

- **Nothing is submitted without your Submit tap.** Approving a match only
  *prepares* it: the engine reads the form, fills what it can and drafts a cover
  letter. The Review screen shows exactly what will be sent, every field is
  editable, and only pressing Submit there sends anything.
- **Demographic questions are never answered.** Gender, race, veteran and
  disability fields are matched by rule and deliberately left blank, as are
  salary-expectation fields. Those are yours to answer or decline.
- **CAPTCHAs are never bypassed.** A CAPTCHA, login wall or bot check stops the
  submission, marks it `needs_you`, and pushes you a link to finish it yourself.
- **LinkedIn Easy Apply is not automated.** Automating it violates LinkedIn's
  terms, so those postings route to you. `apply.manualOnlyHosts` controls the
  list.
- **There is a daily cap.** 15 submissions by default, configurable in
  Preferences, enforced server-side.
- **Everything is logged.** Every generated cover letter and every filled form
  is stored, so you can see exactly what was sent on your behalf.

## Updating without reinstalling

Both apps keep themselves current. You install once.

**Android** has two layers. Almost every change is JavaScript, and those ship as
over-the-air updates: the app fetches them on launch and applies them on the
next start, with no install step and nothing for you to do. When a change needs
a new native binary — a new permission, an SDK bump — the release feed tells the
app, Today shows a hairline banner, and tapping it downloads the APK and hands
it to the system installer. Android does not allow a silent install of a
sideloaded package, so you confirm once. That single tap is the only manual step
there ever is.

**Desktop** uses Tauri's updater. It checks a manifest CI publishes, downloads
in the background, and swaps the build in on relaunch. Every update is
signature-checked against a public key compiled into the app, so a compromised
host cannot push a build of its own.

### Cutting a release

**Nothing is published until you tag.** There is no APK, no installer and no
release feed until the release workflow has run at least once — the in-app
updaters have nothing to find before then, and the first install of each app is
always manual. That is the only manual install there ever is, but it does have
to happen.

Before the first tag, four things have to be true:

1. **A default branch exists and has this code on it.** The release workflow
   checks out and pushes to the repository's default branch.
2. **The Android signing secrets are set** — `ANDROID_KEYSTORE_BASE64`,
   `ANDROID_KEYSTORE_PASSWORD`, `ANDROID_KEY_ALIAS` and `ANDROID_KEY_PASSWORD`.
   Without them the APK job fails and no APK is attached.

   Generate the keystore once and keep it somewhere permanent:

   ```bash
   keytool -genkeypair -v -keystore herald.keystore -alias herald \
     -keyalg RSA -keysize 4096 -validity 10950
   base64 -w0 herald.keystore    # paste into ANDROID_KEYSTORE_BASE64
   ```

   **Losing this key is unrecoverable.** Android refuses to install a build
   signed with a different key over an existing one, so a lost keystore means
   uninstalling and reinstalling by hand — the exact thing Herald exists to
   avoid. No Expo account is needed: the APK is built with Gradle on the
   runner. `EXPO_TOKEN` is optional and only enables over-the-air updates.
3. **The desktop signing key is set** — `TAURI_SIGNING_PRIVATE_KEY` and its
   password, with the public half in `tauri.conf.json`. Without it the desktop
   installers build but no update manifest is produced, so desktop updates are
   never offered.
4. **GitHub Pages is enabled** for the repository, with the source set to
   GitHub Actions.

Then:

```bash
git tag v1.4.2 && git push origin v1.4.2
```

That cuts `## [Unreleased]` from the CHANGELOG into a dated section and
publishes it four ways: as the GitHub Release body, as `releases/index.json`
for both in-app **What's new** screens, as the two updater manifests, and as a
public release-notes page on GitHub Pages. The APK is attached to the GitHub
Release, and its URL is written into `releases/index.json` as `androidApkUrl`,
which is what the in-app updater reads.

A pull request that changes `apps/**` or `packages/core/**` without adding a
CHANGELOG entry fails CI. Release notes are not a habit here; they are a gate.

### Why the app might not see an update

Work down this list — it is ordered by how often each one is the cause:

| Check | Where |
|---|---|
| A release exists at all | The repository's Releases page |
| The APK is attached to it | Same page, under Assets |
| `androidApkUrl` is set in the feed | `releases/index.json` |
| The app knows where the feed is | `HERALD_RELEASES_INDEX_URL` at build time, or `releases.indexUrl` in the engine config |
| The published version is newer | An equal or older version is correctly ignored |
| "Install unknown apps" is allowed | Android settings, for Herald |

### Secrets CI needs

| Secret | For | Required |
|---|---|---|
| `ANDROID_KEYSTORE_BASE64`, `ANDROID_KEYSTORE_PASSWORD`, `ANDROID_KEY_ALIAS`, `ANDROID_KEY_PASSWORD` | Signing the APK | Yes, for Android |
| `TAURI_SIGNING_PRIVATE_KEY`, `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` | Signing desktop updates | Yes, for desktop self-updates |
| `EXPO_TOKEN`, `EAS_PROJECT_ID` | Over-the-air JavaScript updates | No — the APK path works without them |
| `APPLE_*` | macOS notarization — without it Gatekeeper blocks the updater | Only for macOS |

Generate the Tauri signing key with
`npm run tauri -w @herald/desktop -- signer generate`, then put the public half
in `apps/desktop/src-tauri/tauri.conf.json` under `plugins.updater.pubkey`.

## Configuration

Everything operational resolves in this order, last wins:

1. schema defaults
2. `services/engine/config/default.json`
3. the file at `HERALD_CONFIG`, or `./herald.config.json`
4. environment variables

Some of what that covers:

| | |
|---|---|
| `sources` | Which boards to read, and how |
| `llm.scoreModel` / `writeModel` | Which models to use |
| `llm.promptDir` | Prompt templates — editable without rebuilding |
| `apply.fieldRulesFile` | How form fields map to your profile |
| `apply.manualOnlyHosts` | Hosts Herald will never automate |
| `schedule.crawlCron` | How often to scan |
| `matching.feedFloor` | The score below which nothing becomes a match |
| `notifications.fcmServiceAccountFile` | Push credentials |
| `tracking.*` | Optional Gmail reply tracking |

See `services/engine/herald.config.example.json` for a fully worked example and
`services/engine/.env.example` for every environment variable.

## Development

```bash
npm install
npm run build                    # core + engine
npm run typecheck                # every workspace
npm run test                     # every workspace

npm run engine:dev               # engine with reload
npm run tauri:dev -w @herald/desktop
npm start -w @herald/android
```

Design tokens live in one place: `packages/core/src/tokens.ts`. The Android app
imports them directly; the desktop app's CSS is generated from them by
`scripts/generate-css-tokens.mjs`, and CI fails if the generated file is stale.
Change a value there and both apps follow. The same is true of the icons, which
`scripts/build-icons.mjs` draws from the emblem, and of every user-facing
string, which lives in `packages/core/src/strings.ts`.

The original design handoff is preserved under `design-handoff/`.
